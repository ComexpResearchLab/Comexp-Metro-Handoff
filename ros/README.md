# Детектор препятствий метро — узел ROS 2 и контейнер

Обнаружение посторонних объектов на пути перед беспилотным поездом метро по данным лидара
Hesai OT128. Этот каталог оборачивает детекционный движок (`libmetro_core.so`, разделяемая
библиотека с C-ABI) в узел ROS 2 Humble и образ Docker.

```
PointCloud2 --> декодирование (numpy, без копирования) --> [пересборка сетки, если это не 128-лучевая сетка драйвера]
            --> libmetro_core.so: одометрия (ICP + захват скорости при инициализации) -> геометрия пути
                -> обнаружение -> сопровождение -> тревоги
            --> /metro/alerts (JSON), /metro/obstacle, /metro/obstacle_distance,
                /metro/markers (RViz), /metro/status (JSON), /diagnostics
```

## Сборка

Из корня репозитория (контексту сборки нужен каталог `ros/`):

```bash
docker build -f ros/Dockerfile -t metro_detector .
```

## Запуск

Сеть хоста, чтобы контейнер видел топики, публикуемые на хосте (драйвер лидара, `ros2 bag play`):

```bash
docker run --rm -it --net=host --ipc=host metro_detector
```

Воспроизведение записи (во втором терминале; каталог записи содержит `metadata.yaml` + `*.db3`):

```bash
docker run --rm -it --net=host --ipc=host -v /path/to/bags:/bags metro_detector \
    ros2 bag play /bags/roundT_doubleT --qos-profile-overrides-path /opt/metro/tools/qos_replay.yaml
```

Переопределение QoS (reliable, history 200) важно: записи набора данных несут историю писателя,
равную 10, и с ней `ros2 bag play` терял 3–5 % облаков размером 5–8 МБ на частоте 10 Гц на нашем
тестовом стенде; одометрия движка рассчитывает на последовательные кадры, и каждый потерянный кадр
снижает качество сопровождения. С переопределением и очередями без потерь узел принимал и
обрабатывал каждый кадр на частоте датчика (см. «Производительность»). `-e METRO_FASTDDS_LARGE=1`
включает профиль Fast DDS с сегментом разделяемой памяти 128 МБ (`/opt/metro/fastdds_large.xml`;
нужен `--ipc=host` или `--shm-size=1g`); он убрал потери на `roundT_doubleT`, но не на записи
организаторов, поэтому по умолчанию выключен.

Просмотр выхода:

```bash
docker run --rm -it --net=host --ipc=host metro_detector ros2 topic echo /metro/alerts
docker run --rm -it --net=host --ipc=host metro_detector ros2 topic echo /metro/obstacle_distance
```

Всё в одном контейнере (узел в фоне, затем запись):

```bash
docker run --rm -it --shm-size=1g -v /path/to/bags:/bags metro_detector bash -c \
  "ros2 launch metro_detector metro_detector.launch.py verbose:=true & sleep 5; \
   ros2 bag play /bags/cloud_with_fake_obj --qos-profile-overrides-path /opt/metro/tools/qos_replay.yaml; sleep 10"
```

RViz 2 на хосте с настольной установкой ROS 2: `rviz2 -d ros/metro_detector/config/metro.rviz`
(фиксированная система координат `hesai_lidar`; для записи `doubleT_obstacle` укажите `lidar_livox`),
либо `ros2 launch metro_detector metro_detector.launch.py rviz:=true` там, где установлен rviz2.

## Топики

| Топик | Тип | Содержимое |
|---|---|---|
| вход: `/lidar_points`, `/sensing/lidar/hesai128/pointcloud` | `sensor_msgs/PointCloud2` | оба топика набора данных по умолчанию; отдельный трекер на каждый топик |
| `/metro/alerts` | `std_msgs/String` | JSON, по одному на входной кадр (ниже) |
| `/metro/obstacle` | `std_msgs/Bool` | в этом кадре объявлена тревога о препятствии |
| `/metro/obstacle_distance` | `std_msgs/Float32` | расстояние вперёд (м) до ближайшего препятствия с тревогой, `-1` если нет |
| `/metro/markers` | `visualization_msgs/MarkerArray` | красный параллелепипед + подпись на каждое препятствие, зелёная ось пути |
| `/metro/status` | `std_msgs/String` | JSON на кадр: захват одометрии, задержка кадра, входная частота, счётчики |
| `/diagnostics` | `diagnostic_msgs/DiagnosticArray` | 1 Гц; WARN, пока одометрия выходит на режим |

JSON топика `/metro/alerts`:

```json
{"stamp": 1790252237.24, "frame_id": "hesai_lidar", "topic": "/lidar_points", "seq": 812,
 "obstacle": true, "nearest_distance": 96.4,
 "alerts": [{"id": 57, "distance": 96.4, "lateral": 0.12, "height": 1.63, "n_points": 41, "hits": 5,
             "first_alert_distance": 118.2, "new": false}],
 "odometry": {"locked": true, "ds": 1.9312, "s": 1520.4, "event": null},
 "geometry": {"ok": true, "reach": 180.0, "los_horizon": 190.0, "degraded": null}}
```

- `distance`: метры вперёд от датчика вдоль пути; `lateral`: метры от оси пути (положительное -
  вправо); `height`: верх объекта над линией головок рельсов (м).
- `first_alert_distance`: расстояние, на котором объект был объявлен впервые; `new`: первый кадр
  этой тревоги.
- `odometry.locked`: движок измеряет собственный пройденный путь (ICP «точка-плоскость») и
  подавляет тревоги в первых кадрах, пока скорость не захвачена (в среднем 2 кадра от холодного
  старта).

## Параметры

| Параметр | По умолчанию | |
|---|---|---|
| `input_topics` | `['/lidar_points', '/sensing/lidar/hesai128/pointcloud']` | топики PointCloud2 |
| `alerts_topic`, `obstacle_topic`, `distance_topic`, `markers_topic`, `status_topic` | см. «Топики» | имена выходов |
| `frame_id` | `''` | система координат маркеров; пусто = собственный `frame_id` облака |
| `verbose` | `false` | логировать каждый кадр (иначе — только новые тревоги) |
| `publish_markers` | `true` | маркеры RViz |
| `qos_depth` | `100` | история читателя DDS (колбэк подписки только ставит в очередь, поэтому обычно здесь не больше кадра) |
| `max_queue` | `1` | кадров в очереди на стадию (декодирование, движок) после захвата одометрии; более старые кадры отбрасываются, когда движок отстаёт (учитываются в `/metro/status` `dropped_frames`, логируется раз в секунду) — задержка остаётся ограниченной. Безопасно начиная с `metro_version` 7: одометрия перекрывает пропущенные кадры по временным меткам заголовка |
| `warmup_queue` | `20` | предел, пока одометрия не захвачена (старт, потеря захвата): каждый кадр сохраняется (2 с) — захвату при инициализации нужны последовательные кадры, а незахваченный кадр после пропуска регистрируется примерно с 4-кратного числа стартов; после захвата накопившиеся кадры разбираются в пределах `max_skip` |
| `max_skip` | `0.5` | с: стадия никогда не отбрасывает столько кадров, чтобы метки обработанных кадров скакнули больше, чем на это значение — накопление (инициализация, медленный кадр) разбирается по одному кадру за 0.5 с (5 кадров, дёшево перекрывается одометрией) до наверстывания, а не одним скачком |
| `use_stamps` | `true` | передавать движку временную метку заголовка PointCloud2 (`metro_version` >= 7); `false` = предполагаются последовательные кадры (прежнее поведение) |
| `rust_regrid` | `true` | пересобирать облака без поля `ring` в библиотеке движка (`metro_version` >= 7, побайтово идентично, ~20 мс вместо ~100 мс); `false` или более старая библиотека = пересборка на Python |
| `qos_reliable` | `true` | reliable (драйвер Hesai для ROS 2 и `ros2 bag play` набора данных публикуют reliable; подписка best-effort теряла ~60 % кадров организаторов на 10 Гц); `false` для издателя best-effort (об этом сообщит предупреждение о несовместимом QoS) |
| `record_path` | `''` | дописывать по одной строке JSON на кадр (автономные проверки) |
| `publish_detections` | `false` | добавлять в JSON тревог сырые покадровые обнаружения |
| `library` | `''` | библиотека движка; по умолчанию `$METRO_LIB` = `/opt/metro/lib/libmetro_core.so` |

Аргументы launch-файла носят те же имена:
`ros2 launch metro_detector metro_detector.launch.py input_topics:="['/my/cloud']" verbose:=true`.

## Формат входных данных

PointCloud2 драйвера Hesai, как в наборе данных: поля `x, y, z, intensity` (float32), `ring`
(uint16), `timestamp` (float64), сетка двойного отражения в столбцовом порядке (слот = столбец * 128
+ ring; каждый импульс дважды — последнее и сильнейшее эхо), пустые отражения как нули. Сообщение
декодируется по собственной таблице полей (любые смещения / point_step). Облако не в этой раскладке
— без поля `ring` (синтетическая запись организаторов `cloud_with_fake_obj`), число точек не кратно
128, точки переупорядочены или отфильтрованы по NaN — пересобирается на сетку 128 x 2400 по
геометрии лучей (угол места -> канал лазера, азимут -> столбец импульса, измеренная таблица датчика
`sensor_hesai128.npz`) до того, как его увидит движок. Вперёд — это -y, поперёк — x, вверх — z.

## Автономная проверка (узел == движок)

`ros/tools/bag_check.sh <каталог записи> <record.jsonl> [rate]` (внутри контейнера) прогоняет запись
через узел с очередью без потерь и записывает по одной строке JSON на кадр; `ros/tools/compare_alerts.py
<record-a.jsonl> <record-b.jsonl>` сравнивает две такие записи (тревоги, одометрия, покрытие кадров)
и печатает задержку узла. `ros/tools/engine_bench.py <bag.db3>` замеряет покадровую работу
(декодирование + пересборка сетки + шаг движка) без ROS, а `ros/tools/node_sim.py` прогоняет стадии
узла на записи без слоя DDS.

На наших тестовых данных узел в точности воспроизводит покадровый результат самого движка:

| запись | кадры | узел == движок | объектов с тревогой (первый кадр / расстояние совпадают) |
|---|---|---|---|
| `cloud_with_fake_obj` организаторов (без поля ring, пересобрана) | 1510 / 1510 | равны в каждом кадре | 13 |
| `doubleT_obstacle` (`/sensing/lidar/hesai128/pointcloud`, 921 тыс. точек) | 201 / 201 | равны в каждом кадре | 5 |
| `roundT_doubleT` (чистая) | 252 / 252 | равны в каждом кадре | 0 |

«Равны» означает те же объекты с тревогой, с теми же целочисленными полями в каждом кадре, дробные —
в пределах 1e-6 м. Измеренные расхождения не превышают 2.3e-13 м (разница libm между glibc хоста и
образа; тот же бинарник библиотеки побайтово идентичен при разном числе потоков).

## Производительность

На кадр, 8 потоков ядра сервера Xeon (`ros/tools/engine_bench.py`, без ROS; и узел, воспроизводящий
на частоте датчика с очередью без потерь):

| | декодирование (+ пересборка) | движок | кадр |
|---|---|---|---|
| формат набора данных, 307 тыс. точек (`roundT_doubleT`) | 4 мс | p50 63–75 мс, p90 86–92 мс | успевает за 10 Гц |
| формат организаторов (пересборка на Python, совмещена с движком) | 98 мс | p50 60 мс, p90 66 мс | задержка 162 мс, успевает за 10 Гц |
| формат организаторов, пересборка в движке (`metro_version` 7) | 18–25 мс | | см. таблицу задержек ниже |
| широкий формат, 921 тыс. точек (`doubleT_obstacle`) | 19 мс | p50 120 мс | медленнее 10 Гц на этом старом ядре сервера |

Один поток: движок p50 160 мс (формат набора данных). Первые кадры после старта выполняют
аккуратную незахваченную регистрацию (до ~250 мс) и создают накопление в несколько секунд, которое
узел затем разбирает. `RAYON_NUM_THREADS` задаёт число потоков движка (по умолчанию — все ядра).
Стенд поставки (Intel i7-9700E) быстрее на ядро, чем наш сервер разработки.

**Пропущенные кадры (`metro_version` 7).** Раньше одометрия движка предполагала последовательные
кадры: потерянный или отброшенный кадр мог привести к потере захвата скорости, запуску более
медленной незахваченной регистрации, дальнейшему отставанию и повторному «открытию» объектов как
новых треков, поэтому узел никогда не отбрасывал кадры (глубокие очереди), и его задержка росла
неограниченно под нагрузкой. Теперь узел передаёт движку временную метку заголовка, и его одометрия
перекрывает пропущенные кадры (пройденный путь = число кадров с момента опорного × скорость;
пропуски больше 1 с перезапускают инициализацию) и хранит только новейшие кадры (`max_queue`).
Измерено с намеренно отброшенными кадрами (каждый 2-й / 3-й, 10 / 30 % случайно, пачки по 3–5):
потери захвата 12–76 за прогон -> 0, дрейф пройденного пути до 833 м -> меньше 4 м, запись
организаторов с отбрасыванием каждого 3-го кадра 1 - 13 из 13 объектов. Оставшееся ограничение: при
УСТОЙЧИВО пониженной частоте кадров (каждый 2-й / 3-й кадр, 30 % случайно) несколько известных
конструкций дают одиночные ложные тревоги (счётчики-вето трекера видят меньше кадров); поэтому узел
отбрасывает кадры только когда движок отстаёт.

Декодирование кадра из 921 600 точек занимает 12–16 мс (Ryzen); большие значения `decode` в
`/metro/status` включают ожидание в очереди подготовки (например, пока выполняются кадры
инициализации).

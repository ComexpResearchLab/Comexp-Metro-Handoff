# Архитектура

## Обзор

Система состоит из двух частей:

1. **Узел ROS 2** (`ros/metro_detector`) - приём и декодирование облаков точек, публикация
   результата в топики ROS 2. Написан на Python (rclpy) поверх библиотеки движка через ctypes.
2. **Движок обнаружения** (`libmetro_core.so`) -- вся вычислительная логика: одометрия,
   построение геометрии пути и тоннеля, обнаружение и сопровождение объектов. Библиотека с C ABI;
   в репозиторий не входит и загружается при сборке (см. активацию).

Разделение сделано намеренно: узел - это тонкая, легко проверяемая обвязка, а движок --
детерминированное ядро без ROS-зависимостей, которое можно вызывать и вне ROS (для отладки и
измерений).

## Поток данных

```
sensor_msgs/PointCloud2
      |
      v
декодирование (numpy, без покадровой обработки на Python)
      |
      v
[перестройка на регулярную сетку датчика, если облако не в формате драйвера,
 например синтетические записи организатора без поля ring, или данные других сенсоров]
      |
      v
libmetro_core.so за один вызов:
   одометрия (ICP по облакам точек + захват скорости на разгоне)
   -> геометрия пути (рельсы, ось пути, в т.ч. на кривых)
   -> модель сечения тоннеля (стены, свод)
   -> габаритный коридор поезда (2,1 x 3 м)
   -> обнаружение объектов в коридоре
   -> сопровождение и подтверждение
      |
      v
публикация в топики ROS 2
```

Датчик: Hesai OT128, 128 лучей, 10 кадров в секунду. Система координат: вперёд -y, поперёк x,
вверх z. На каждый входной топик создаётся отдельный независимый трекер.

## Топики

| Топик | Тип | Содержимое |
|---|---|---|
| вход: `/lidar_points`, `/sensing/lidar/hesai128/pointcloud` | `sensor_msgs/PointCloud2` | оба имени по умолчанию |
| `/metro/alerts` | `std_msgs/String` | JSON, по одному на кадр |
| `/metro/obstacle` | `std_msgs/Bool` | в кадре есть подтверждённое препятствие |
| `/metro/obstacle_distance` | `std_msgs/Float32` | расстояние (м) до ближайшего препятствия, `-1` если нет |
| `/metro/markers` | `visualization_msgs/MarkerArray` | рамка и подпись объекта, ось пути (для RViz) |
| `/metro/status` | `std_msgs/String` | JSON: захват одометрии, задержка кадра, частота входа, счётчики |
| `/diagnostics` | `diagnostic_msgs/DiagnosticArray` | 1 Гц; WARN на этапе разогрева одометрии |

Поля тревоги (`/metro/alerts`): расстояние вперёд по пути, смещение от оси (право положительно),
высота над головкой рельса, число точек, число подтверждающих кадров, дальность первого
срабатывания. Полный пример JSON и все параметры узла -- в [../ros/README.md](../ros/README.md).

## Реальное время и потеря кадров

Одометрия принимает метку времени каждого кадра (заголовок PointCloud2) и «перешагивает»
пропущенные кадры, оценивая пройденный путь по времени, а не по числу кадров. Благодаря этому
узел может безопасно отбрасывать устаревшие кадры при перегрузке и держать ограниченную задержку,
вместо того чтобы копить очередь. На этапе захвата скорости (старт, потеря захвата) кадры не
отбрасываются - разогреву нужны последовательные кадры.

Бюджет времени: порядка 68-120 (в зависимости от сенсора) мс на кадр в реальном Docker на целевом классе оборудования,
что укладывается в 10 Гц. Подробные измерения - в [experiments.md](experiments.md).

## Сборка образа

Многоэтапный `ros/Dockerfile` на базе `ros:humble-ros-base` (Ubuntu 22.04). На этапе сборки
выполняется активация (загрузка движка, привязанного к машине), затем собирается ROS-пакет узла.
Запуск образа сети не требует. Полное описание сборки и запуска -- в [../ros/README.md](../ros/README.md).
